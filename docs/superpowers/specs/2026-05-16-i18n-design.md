# Design: Thai/English i18n for the admin frontend

- **Date:** 2026-05-16
- **Status:** Approved
- **Scope:** `frontend/` (Next.js 14 admin panel) plus one CI step — no backend code changes

## Background

The admin frontend (`frontend/`, Next.js 14.2.5 App Router) has all UI text
hardcoded as English string literals in JSX across ~10 pages plus the nav and
login. There is no i18n layer. The backend already returns a stable
`error.code` on every error response (`{ error: { code, message, details } }`),
so localized error text can be derived on the client without backend changes.

## Goals

- Support two languages: **Thai** and **English**, with **Thai as the default**.
- Localize all user-facing UI text in `frontend/`.
- Localize API error messages by mapping the backend `error.code`.
- Let the user switch language at runtime; the choice persists across reloads.

## Non-goals (YAGNI)

- No localized date/number/currency formatting — `lib/format.ts` is untouched.
  Only text is translated.
- No ICU pluralization/gender. next-intl supports it later if needed.
- No locale in the URL, no `app/[locale]/` restructure, no middleware.
- No backend changes. API error `code`s are localized client-side.

## Decisions

| Question | Decision |
|----------|----------|
| Languages / default | Thai + English; default Thai |
| Scope | Frontend UI + API error messages |
| Library | `next-intl` |
| Routing mode | Without i18n routing — locale in a cookie, `app/` layout unchanged |

## Architecture

`next-intl` in its **without-i18n-routing** setup:

- Locale lives in a cookie named `locale` with value `th` or `en`. Missing or
  invalid → `th`.
- `app/` directory structure is unchanged. No `middleware.ts`.
- `app/layout.tsx` (a Server Component) resolves the locale, sets `<html lang>`,
  and wraps the tree in `NextIntlClientProvider`, passing the message catalog.
- Every page that renders translatable text is a Client Component
  (`"use client"`; they use React Query hooks); each uses the
  `useTranslations()` hook to read text. `app/page.tsx` only redirects and
  has no text.

### Data flow

```
request ──> i18n/request.ts (reads `locale` cookie, default th)
         ──> loads messages/<locale>.json
         ──> layout.tsx: <html lang>, <NextIntlClientProvider messages>
         ──> client pages: useTranslations('namespace') -> t('key')
```

Switching language: a client `LocaleSwitcher` sets the `locale` cookie via
`document.cookie` (`path=/`, `max-age=31536000`, `SameSite=Lax`) and calls
`router.refresh()`. The refresh re-runs the server layout, which reads the new
cookie and re-renders every page in the new language. React state and the auth
token (in `localStorage`) are preserved.

## Message catalog

`messages/th.json` and `messages/en.json` share the same key tree, grouped into
namespaces. Initial namespaces (extended as pages are migrated):

- `common` — shared words: save, cancel, loading, search, actions, yes/no.
- `nav` — menu labels, sign in, sign out.
- `login` — the login page.
- `dashboard`, `visits`, `customers`, `products`, `arAging`, `creditRisk`,
  `audit` — one namespace per page.
- `errors` — one key per backend `AppErrorCode`.

## API error localization

The backend `AppErrorCode` union has exactly 11 values, all already returned in
`error.code`:

```
VALIDATION_ERROR  UNAUTHORIZED  FORBIDDEN  NOT_FOUND  CONFLICT  BAD_REQUEST
DOMAIN_RULE_VIOLATION  INSUFFICIENT_STOCK  CREDIT_LIMIT_EXCEEDED
INVALID_STATE  INTERNAL_ERROR
```

The `errors` namespace has one entry per code. `lib/api.ts`'s `ApiError` gains a
`code?: string` field read from `body.error.code`. The `use-error-message` hook:

1. If `err` is an `ApiError` with a `code` that exists in the `errors`
   namespace → return the translated string.
2. Else if `err` is an `ApiError` → return its raw `message` (the English text
   the API already sent).
3. Else → return a generic translated "unexpected error" string.

Pages that currently display `err.message` switch to this hook. Granular
field-level validation detail (`details`) is not localized — `VALIDATION_ERROR`
maps to one generic message.

## Testing

- **Key parity:** `check-messages.mjs` compares the flattened key sets of
  `th.json` and `en.json` and exits non-zero on any difference. Wired into the
  frontend CI job.
- **Type check:** `global.d.ts` makes `tsc --noEmit` (already in CI) flag any
  `t('key')` referencing a key absent from `en.json`.
- **Build:** `next build` (already in CI) must pass.
- **Manual:** load the app, toggle TH/EN on every page, confirm text switches
  and persists across reload; trigger a real API error (e.g. insufficient
  stock on a load) and confirm the message is localized.

## Notes

- `next-intl` is pinned to a version verified compatible with Next.js 14.2.5
  during implementation (the without-routing cookie setup is supported in the
  3.x line).
- `app/layout.tsx`'s `metadata.title` stays as the current static English
  string; localizing document `<title>` is optional and out of scope here.
